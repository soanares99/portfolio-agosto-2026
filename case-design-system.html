Scaling the Design Foundation for Loans

How I architected a local component library and template system for PicPay's Loans Business Unit, built on top of the company's global Design System — reducing design fragmentation and speeding up handoffs.

01

Context & Problem

The challenge of scaling without structure

PicPay is one of Brazil's largest fintechs, with millions of users across a full financial ecosystem. The Loans Business Unit spans multiple credit products — personal loans, salary-linked loans, FGTS-backed credit, and more — each with its own squad and specific user needs.

The problem
  • Every squad designing loan flows from scratch
  • Visual, content, and UX inconsistency across credit products
  • PicPay launching a new Design System, requiring every product to update
  • Heavy dependency on the global Design System, which didn't cover credit-specific flows
  • Repeated work: the same components built over and over by different designers
  • Painful onboarding for new designers — no documentation, no reference
The opportunity
  • Centralize design knowledge from every Loans product into a single library
  • Create a specialization layer on top of the global DS — not a fork
  • Let any designer or squad move faster with tested components
  • Document patterns in a structured, semantic way — enabling AI-assisted design flows
  • Reduce rework and free up design capacity for innovation instead of repetition
  • Establish design governance and a contribution model that scales with the team

The process

Four phases, one cohesive system

Phase 1 Discovery & Audit

The trigger was the launch of a new PicPay Design System. Before building anything, I needed to answer two questions: what do we already have? And what does the new DS actually cover for us?

What we had

I mapped the existing screens across every Loans squad — full flows, edge cases, empty and error states. The goal was to understand what was actually in use, not what we assumed existed.

What the new DS covers

I analyzed PicPay's newly launched DS to understand which components and patterns already served the Loans context — and where it fell short for credit-specific flows.

Recurring patterns

I identified UI patterns that showed up consistently across products: simulators, installment selectors, contract summaries, progress indicators — the candidates for the library.

Gaps & scope of adaptation

I defined what needed to be rebuilt from scratch, what could be adapted from the new DS, and what was too Loans-specific to live anywhere but our own library.

This phase didn't produce a formal deliverable — it produced clarity: a shared understanding of what the new DS gave us, what it didn't, and what we'd need to build or change along the way.

Phase 2 Architecture & File Structure

One of the key decisions was how to divide responsibility — not just within components, but across the files themselves. Every file has a clear owner and a single purpose.

Main Library File
The single source of truth — every component, ready to use across all Loans squads.
Product Designers
Component source files
One file per component — the editable source. Changes happen here, then propagate to the main library.
Contributors
Tracking file
Baseline tracking definition for every component — events, properties, and expected behaviors documented at the source.
Product Designers
Accessibility file
Defines how each component should be read and navigated — screen reader behavior, ARIA roles, focus order, and contrast rules.
Product Designers
Handoff file
Full usage and implementation spec — spacing, states, behavior rules. Everything a developer needs without having to ask.
Developers

This structure ensures every audience gets exactly what they need — and nothing they don't. Designers work with confidence. Developers get total clarity. Contributors know where and how to make changes without breaking anything.

Phase 3 Library Build

Ship fast, iterate often — we prioritized whatever delivered the most value first.

Prioritization criteria

1st
Acquisition journey

Components from the contracting flow came first — it's where revenue happens, making it the highest-impact journey to optimize.

2nd
Frequency of use

Within that scope, components were ordered from most to least used across journeys — maximizing the impact of every delivery.

Build order

Components first

Made available to PDs as soon as they were ready, so the team could start using them right away without waiting for the full documentation layer.

Tracking & accessibility in parallel

Once the components layer was stable, the focus shifted to completing the tracking definitions and accessibility specs for each one.

Handoff on squad demand

Released when a squad was about to start development, not ahead of time. This kept the spec current and avoided documentation drift.

Phase 4 Evangelization, ongoing

Building the library was the easy part. Getting people to actually use it — and keep using it — is the work that never ends.

Product Designers

Onboarding sessions for new PDs joining the unit. Ongoing support whenever squads start new flows — making sure they reach for the library first.

Developers

Communicating what changed, when, and why. Keeping handoff files up to date so developers can trust the spec they receive.

Awareness

Sharing updates and new additions with the team. Making the library visible — so people know it exists and when to use it.

Contributions

Reviewing component proposals from other designers. Deciding what belongs in the library vs. what stays local to a squad.

A library without adoption is just a Figma file. Evangelization is the product. Components only have value if the team reaches for them — and that takes constant presence, communication, and trust-building.

04

The Local Library

A system built for loans, by loans

Foundation

Global DS — consumed, not rebuilt. The library holds no tokens, colors, or typography — those live in PicPay's Design System. The Loans library consumes them as-is, guaranteeing total consistency without duplication.

Components

Loans-specific building blocks. Built on top of existing global DS components — extended and combined to serve credit product flows that the global DS doesn't cover.

Templates

Flow templates. Pre-assembled screens for the most critical Loans flows — start designing in minutes, not hours.

Documentation

One file per audience. Every component ships with dedicated files so each stakeholder gets exactly what they need — no more, no less.

Learnings & Next Steps

What I learned & where I'd go from here

What worked
Specialization-layer strategy

Positioning the library as an extension of the global DS — not a competitor — meant faster buy-in from both the design system team and the engineers who already knew the global tokens.

Starting with templates, not atoms

Shipping full flow templates from the start created immediate value and convinced hesitant squads to adopt before the full library was even ready.

Cross-functional alignment from day one

Involving engineers in the architecture phase avoided the classic "this doesn't match how we build" feedback during handoff.

What I'd do differently
Semantic naming from day one

I rolled out semantic naming as the library evolved, but starting with it from the beginning would have unlocked AI capabilities faster — something I'm now building retroactively.

Defining a contribution model earlier

Governance was an afterthought in the early phases — I'd set up the contribution process before the first outside designer ever touched the library.

Vision & Next Steps
Promote high-frequency components into PicPay's global Design System
Share this as a model for other PicPay Business Units (Insurance, Investments)
AI-assisted documentation generation (in progress)

The library's semantic structure turned out to be AI-ready. I'm now building an AI layer that automatically generates tracking specs and accessibility documentation with a single click — removing manual work for PDs. Since every template follows a consistent, predictable pattern, part of the handoff documentation can be automated.
